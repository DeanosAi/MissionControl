# Mission Control VPS Preparation - Phase 1

## Objective

Prepare Mission Control for later VPS hosting without deploying yet and without breaking the existing local workflow on `http://localhost:3000`.

## What Phase 1 changed

### Runtime and environment handling

- Added shared runtime config in `src/lib/runtime.ts`.
- Added environment-variable overrides for:
  - `MISSION_CONTROL_DATA_DIR`
  - `MISSION_CONTROL_DOCS_DIR`
  - `MISSION_CONTROL_MEMORY_DIR`
  - `MISSION_CONTROL_BASE_URL`
  - `HOST`
  - `PORT`
- Kept current local defaults intact so local development still reads from repo `data/` and `docs/`.

### Data path strategy

- Replaced hard-coded `process.cwd()/data` assumptions with shared helpers.
- Added `scripts/prepare-runtime.mjs` to create the configured data directory and seed `tasks.json`, `team.json`, and `events.json` if a future VPS data path starts empty.
- This preserves JSON-backed storage for now while making it easy to move those files onto a persistent VPS path later.

### Production readiness

- Added `/api/health` for uptime/readiness checks.
- Added `npm run build:prod`, `npm run start:prod`, `npm run prepare:runtime`, and `npm run healthcheck`.
- Disabled the Next.js `X-Powered-By` header in `next.config.ts`.
- Updated the Windows production launcher to run runtime preparation before serving.

## Recommended VPS shape later

### App process

- Run Mission Control behind a process manager such as `systemd`, `pm2`, or Docker restart policy.
- Use `npm run build:prod` during release/update.
- Use `npm run start:prod` for the live app process.

### Reverse proxy

- Put Nginx or Caddy in front of the app.
- Proxy public traffic to the internal Next.js process on `127.0.0.1:3000`.
- Terminate TLS at the reverse proxy.
- Forward standard headers:
  - `Host`
  - `X-Forwarded-For`
  - `X-Forwarded-Proto`
  - `X-Real-IP`

### Persistence

- Keep app code and persistent data separate.
- Recommended persistent directories:
  - app code: `/srv/mission-control/app`
  - JSON data: `/srv/mission-control/data`
  - docs: `/srv/mission-control/docs`
  - memory mirror if wanted on server: `/srv/mission-control/memory`
- Set env vars so deploys do not overwrite runtime data.

## Security readiness notes

- Mission Control currently has no login system. Do not expose it publicly without at least one access control layer.
- Phase 1 recommendation for first deployment:
  - TLS at the reverse proxy
  - HTTP basic auth at the reverse proxy, or VPN / IP allowlist
  - firewall allowing only `80/443` publicly and app port only on localhost
- If public multi-user access is desired later, add proper application authentication in a later phase instead of relying permanently on basic auth.

## Health and startup behavior

- Health endpoint: `GET /api/health`
- Local/default health URL: `http://127.0.0.1:3000/api/health`
- `prepare-runtime` ensures the target data directory exists before the app starts.
- Health output includes:
  - mode
  - host and port
  - resolved data/docs/memory paths
  - writable state for data storage
  - presence/counts for core JSON files

## Deployment checklist for later

1. Confirm VPS OS and access method.
2. Confirm domain or subdomain.
3. Decide reverse proxy choice: Nginx or Caddy.
4. Decide access-control method:
   - Basic auth
   - VPN only
   - IP allowlist
   - Later app auth phase
5. Create persistent directories on the VPS.
6. Set `.env` values for production paths and public URL.
7. Install dependencies and run `npm run build:prod`.
8. Start the app with a process manager using `npm run start:prod`.
9. Point the reverse proxy to `127.0.0.1:3000`.
10. Verify `/api/health` locally on the server and through the proxy.
